O problema

Agentes não deveriam falar com suas APIs sem supervisão.

✕ Agente → API direto

  • Credenciais no prompt, no config do cliente ou no histórico do chat.
  • CPF, salário e e-mail vão inteiros para o contexto do modelo.
  • Respostas enormes estouram o contexto e o custo.
  • Ninguém sabe quem chamou o quê, quando e por quê.
  • Toda API precisa ser reescrita como servidor MCP.

✓ Agente → gateway → API

  • Credenciais ficam num cofre e são injetadas por chamada.
  • PII sai mascarada antes de chegar ao modelo.
  • A resposta é recortada para caber no contexto.
  • Cada chamada gera um evento de auditoria.
  • A API continua exatamente igual.
  • Pergunte à plateia: quem já colou um token de API num config de MCP? (quase todo mundo)
  • O ponto central: o modelo é um cliente não confiável. Tudo o que entra no contexto pode vazar, ser logado ou ser repetido.

Tools

Funções que o modelo pode chamar, com JSON Schema de entrada e saída. Ex.: rh_colaborador_get.

Resources

Conteúdo que o host lê sob demanda. O gateway usa para artifact:// (respostas grandes) e ui:// (interfaces).

Transporte

Streamable HTTP, com o token no header Authorization. Specs 2025-11-25 e 2026-07-28.

  • Para quem é de produto: MCP é o padrão aberto que deixa qualquer agente usar qualquer ferramenta.
  • O gateway é um Server MCP do lado do agente e um cliente REST do lado da API.
A ferramenta

MCP Gateway

Aponte para um OpenAPI, Postman, HAR ou cURL e o gateway gera as tools. O dono revisa e habilita, e as políticas decidem quem chama o quê.

01

Default deny

Toda tool nasce disabled. Sem policy, ninguém chama.

02

Downstream intocado

A API REST não muda nada: nem código, nem deploy.

03

Credencial invisível

O agente usa um token do gateway; o segredo da API fica no cofre.

04

PII mascarada

CPF, CNPJ, PIS, e-mail e telefone saem mascarados, com hash ou tokenizados.

05

Contexto é escasso

Projeção, limites e artifacts deixam a resposta enxuta.

06

Tudo auditável

Um evento por chamada alimenta auditoria, métricas e traces.

  • Multi-tenant e open source (Apache-2.0); roda com Postgres, Redis e S3/MinIO.
  • Admin UI em React para owners revisarem as tools; Admin API em /admin/v1.
  • Estes seis princípios são o fio da apresentação: volte a eles nas demos.

Agentesó o necessário

O pipeline completo adiciona +4,55 ms no p95, a 200 rps numa única instância e com 0 erros (k6, docs/perf).

  • Leia da esquerda para a direita. O destaque em laranja marca onde a segurança acontece: policy na ida e redaction na volta.
  • Por que performance importa: o gateway fica no caminho de toda chamada, e 4,55 ms é ruído perto da latência de um LLM.
Onboarding

Da API à tool em 5 passos.

  • Importar: OpenAPI 3.x, Swagger 2.0, Postman, HAR ou cURL, com preview antes de salvar.
  • Crawler: um worker gera uma tool por operação, e re-crawls detectam drift.
  • Revisar: a tool nasce disabled; o owner confere schema e anotações.
  • Policy: quem pode chamar, por papel, grupo, usuário ou cliente.
  • Publicar: num servidor virtual /mcp/s/:slug com catálogo próprio.
  • Sem OpenAPI? Cole um cURL ou um HAR exportado do navegador.
  • Também dá para criar tools manuais e tools compostas (JSONata), inclusive descrevendo em linguagem natural no Composer.
Governança

Quem pode chamar o quê, e o que pode sair.

Policies
  • Explicit deny vence allow.
  • Tools destructiveHint só com allow explícito; * não cobre.
  • Rate limit por cliente, no Redis.
PII
  • Detectores: CPF, CNPJ, PIS, CEP, e-mail, telefone, cartão e IBAN.
  • Regras por campo, como saúde e salário.
  • Índice de titular para pedidos LGPD.
  • Exemplo concreto: rh_marcacoes_delete é destrutiva. Mesmo com allow rh_*, o agente não apaga nada sem uma regra nominal.
  • O simulador de policy (/policies/simulate) responde "esse cliente pode chamar essa tool?" antes de ir para produção.
Contexto é escasso

Três jeitos de expor o catálogo.

POST /mcp

Catálogo nativo

Todas as tools permitidas viram tools MCP. Ideal para catálogos pequenos.

POST /mcp/omni

Descoberta sob demanda

search_tools → get_tool_schema → call_tool. Usa ~4% dos tokens de definição de tools.

POST /mcp/s/:slug

Servidor virtual

Catálogo curado e instruções próprias por caso de uso. É o que o ESP32 vai usar.

Projeção

JSONPath para incluir ou excluir campos e limitar arrays e bytes. O agente também pode pedir só o que quer com _fields.

Artifacts

Respostas grandes viram artifact://, lidas em partes com artifact_read e artifact_query.

  • Com 200 tools, só as definições ocupam dezenas de milhares de tokens antes da primeira pergunta. O omni resolve isso com busca.
  • Antecipe o case 2: um modelo de voz pequeno se dá melhor com poucas tools bem descritas, por isso o servidor virtual.
Observabilidade

Um evento por chamada. Tudo deriva dele.

  • CallEvent: tool, cliente, decisão de policy, latência e resultado, sem payload.
  • Alimenta auditoria, Prometheus, traces OpenTelemetry (com traceparent do agente) e dashboard Grafana.
  • Explorador de chamadas e trajetórias de sessão.
  • /mcp/observability: o próprio agente pergunta "quais tools mais falharam hoje?".

Claude conectado ao gateway.

1 · Registrar o servidor no Claude Code 
$ claude mcp add --transport http mcp-gateway \
    http://localhost:4000/mcp/omni \
    --header "Authorization: Bearer mgw_…"
ou · .mcp.json (gerado pela Admin UI) 
{ "mcpServers": { "rh-gestor": {
  "type": "http",
  "url": "https://mcp.empresa.com/mcp/s/rh-gestor",
  "headers": { "Authorization":
    "Bearer ${MCP_GATEWAY_TOKEN}" } } } }
2 · Perguntar

"Quais são os dados do colaborador col-00001 e qual a escala dele esta semana?"

3 · Observar
  • Claude busca a tool com search_tools e chama rh_colaborador_get.
  • O CPF chega mascarado; a credencial da API nunca aparece.
  • Pedir para apagar uma marcação resulta em negado (destructiveHint).
  • Em hosts com MCP Apps, o resultado aparece como tabela ou card (UI generativa).
Roteiro (6 min)
  1. Terminal pronto com pnpm dev, pnpm dev:upstream e o crawler rodando. Admin UI aberta em localhost:5180 (login owner).
  2. Rodar o claude mcp add com o token dev mgw_dev-agent-token-somente-para-desenvolvimento, depois /mcp para mostrar o servidor conectado.
  3. Fazer a pergunta e apontar o CPF mascarado na resposta.
  4. Pedir "apague a última marcação do col-00001" e mostrar a negação da policy.
  5. Abrir o explorador de chamadas na Admin UI: as chamadas estão lá, sem payload.

Limitação para mencionar: conectores do claude.ai que só aceitam OAuth ainda não conectam, porque o gateway autentica com Bearer em header. Claude Code e Desktop com header customizado funcionam.

  • Passe o dispositivo pela plateia ou mostre-o na câmera.

Saída apenas. O pipe abre a conexão; nenhuma porta é aberta no firewall.

PII antes da voz. O CPF é mascarado antes de chegar ao LLM e ao TTS.

Cliente próprio. Token esp32-sala com policy e rate limit dedicados.

  • Caminho de uma pergunta: voz → device → nuvem xiaozhi (o LLM decide chamar uma tool) → endpoint MCP → mcp_pipe.py na sua máquina → gateway → API.
  • O mcp_pipe.py (repositório 78/mcp-calculator) faz a ponte entre o WebSocket do xiaozhi e um servidor MCP via stdio, SSE ou HTTP com headers.
  • Ponto de segurança: a nuvem xiaozhi nunca vê a credencial da API nem o CPF completo.

Gateway · Admin UI
Servidor virtual · assistente-voz

Só 2 tools de leitura: rh_colaborador_get e rh_escalas_list, com instruções curtas e próprias para voz.

Usuário service · token esp32-sala

O nome do token vira o clientId, que aparece nas policies, no rate limit e na auditoria.

Policy

client esp32-sala → allow nas 2 tools; o resto continua em default deny.

Roteiro (8 min)
  1. Admin UI (owner): mostrar o servidor virtual assistente-voz com as 2 tools e a policy do cliente esp32-sala.
  2. Terminal: python mcp_pipe.py, mostrando no log a conexão ao endpoint e o tools/list.
  3. No console xiaozhi.me, o endpoint MCP aparece online com as tools do gateway.
  4. Falar com o device: "Qual a escala do colaborador 1 amanhã?" e depois "Qual o CPF dele?", que vem mascarado.
  5. "Apague a marcação dele" não tem tool no servidor virtual, então o assistente responde que não pode.

Checklist antes do workshop: gateway e crawler com NETWORK_ALLOW_PRIVATE=true (padrão no .env.example de dev, porque a API fake roda em localhost); device no Wi-Fi do evento; testar o pipe na rede do local.

Como começar

Do clone ao primeiro agente em minutos.

$ git clone github.com/leandro-jm/mcp-gateway
$ pnpm install
$ pnpm dev:infra        # Postgres, Redis, MinIO
$ pnpm db:migrate && pnpm db:seed
$ pnpm dev              # gateway :4000
$ pnpm dev:upstream     # API de RH fake :4010
$ pnpm --filter @mcp-gateway/crawler dev
$ pnpm --filter @mcp-gateway/admin-ui dev   # :5180

Perguntas frequentes: OAuth no MCP (no roadmap), suporte a gRPC ou GraphQL (hoje REST; GraphQL pode entrar via cURL ou HAR), custo de latência (4,55 ms p95) e onde roda o LLM do ESP32 (nuvem xiaozhi ou servidor xiaozhi self-hosted).
