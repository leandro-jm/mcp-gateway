# ADR-021: Spec MCP 2026-07-28 e SDK v2

- Status: aceito
- Data: 2026-10-09
- Revisa: ADR-001

## Contexto
A spec MCP 2026-07-28 tornou o núcleo do protocolo stateless:
- não há mais `initialize` nem `Mcp-Session-Id`;
- cada request carrega no `_meta` a versão do protocolo, o `clientInfo` e as capabilities do cliente (`io.modelcontextprotocol/*`);
- `server/discover` substitui o handshake para quem quer as capabilities do servidor antes;
- elicitation e sampling passam a usar `input_required` (multi round-trip);
- extensões (MCP Apps, Tasks) ganharam trilha própria.

O SDK oficial TypeScript publicou a linha v2 (`@modelcontextprotocol/server`, `@modelcontextprotocol/client`, `@modelcontextprotocol/node`, estáveis em 2.x) para essa revisão. O `@modelcontextprotocol/sdk` 1.x segue em manutenção.

A UI generativa (F18) precisa saber, por request, se o cliente declarou a extensão `io.modelcontextprotocol/ui`. No gateway stateless da 2025-11-25 isso não é possível: o `initialize` chega em um request e o `tools/list` em outro, cada um atendido por uma instância nova.

Um spike validou a v2 com o `Server` de baixo nível:
- catálogo dinâmico por tenant usando `authInfo` repassado ao factory;
- capabilities por request em `ctx.mcpReq.envelope`;
- `_meta` próprio preservado no resultado;
- clientes 2025 atendidos pelo fallback stateless do SDK.

## Decisão
- **SDK:** `@modelcontextprotocol/server` e `@modelcontextprotocol/node` **2.x** no runtime do gateway. O `@modelcontextprotocol/sdk` 1.x fica só como devDependency, para os testes que simulam clientes 2025.
- **Protocolo:** alvo **2026-07-28**, mantendo **2025-11-25** e as versões anteriores que o SDK aceita (`SUPPORTED_PROTOCOL_VERSIONS`). A era é decidida pelo SDK em cada request (`createMcpHandler`, com `legacy: 'stateless'`).
- **Montagem:** um `createMcpHandler(factory)` por superfície (`/mcp` e `/mcp/s/:slug` nativos, `/mcp/omni` estático e `/mcp/observability`), adaptado ao Fastify com `toNodeHandler`.
  - A rota continua autenticando e resolvendo o `CallContext`. O contexto chega ao factory pelo `authInfo.extra`, que é pass-through.
  - O factory continua criando um `Server` de baixo nível por request, porque o catálogo é dinâmico por tenant, sujeito e virtual server (motivo original do ADR-001).
- **Contexto do cliente:** `forRequest` passa a ler do envelope a versão do protocolo, o `clientInfo` e as capabilities do cliente, e grava isso em `CallContext.client`.
  - Em requests 2025, a versão vem do header `mcp-protocol-version` como hoje, e as capabilities ficam desconhecidas.
  - A identidade de analytics (ADR-016 §10) passa a usar o `clientInfo` do envelope quando não há `mcp-session-id`.
- **Omni dinâmico:** o modo com sessão (`list_changed` no stream GET) continua **só para clientes 2025**, via `NodeStreamableHTTPServerTransport` com `sessionIdGenerator`.
  - Clientes 2026-07-28 em `/mcp/omni` recebem o modo estático (3 meta-tools); `call_tool` continua alcançando qualquer tool encontrada pela busca.
  - O modo dinâmico para a nova spec (`subscriptions/listen` com o conjunto descoberto chaveado pelo principal) fica para uma fase futura.
- **Cache (`ttlMs`/`cacheScope`):** mantém o padrão do SDK (`ttlMs: 0`, `cacheScope: 'private'`). O catálogo muda sem deploy (publicação, política, projeção), então o gateway não promete cache. Revisar quando houver invalidação por versão do snapshot.
- **Erros:** `McpError` (v1) vira `ProtocolError` (v2), com os mesmos códigos (`-32602` para tool desconhecida). Resource inexistente segue `-32602` com `data: { uri }` na 2026-07-28, como manda a spec.
- **Stateless session id (ADR-016 §10):** continua emitido só no `initialize` de clientes 2025. Clientes 2026-07-28 não têm sessão; a trajetória usa o principal, e `sessionSource` vale `principal`.
- **Elicitation e sampling:** o gateway não usa nenhum dos dois hoje. Se passar a usar, será por `inputRequired(...)`, que atende as duas eras.

## Consequências
- `GET`/`DELETE` em `/mcp`, `/mcp/s/:slug` e `/mcp/observability` continuam `405`. No `/mcp/omni`, só existem para sessões 2025.
- Toda mudança de versão do SDK v2 exige rodar a suíte de integração com os dois tipos de cliente (`@modelcontextprotocol/client` 2.x e `@modelcontextprotocol/sdk` 1.x).
- A F18 (UI generativa) pode decidir por request se emite `_meta.ui`. Em clientes 2025, a regra fica no ADR-022.
- O ADR-001 continua valendo no que não foi revisado aqui: transporte Streamable HTTP, respostas JSON, `Server` de baixo nível e o modelo de erros de tool (`isError: true`).
